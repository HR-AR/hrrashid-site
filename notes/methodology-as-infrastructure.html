Field Note 01

Methodology as Infrastructure

Why I stopped writing prompt libraries and started wiring frameworks into the architecture.

~5 min readBuild in publicAI workflow

Most people treat an AI assistant like a clever intern. You write a good prompt, you hope it remembers, you correct it when it drifts. That works for one task. It falls apart at the fifth.

I run technology for a last-mile delivery operation that moves 100,000 packages a day. The work doesn't arrive one clean task at a time. It arrives as ten half-specified things at once, each touching a different system. The first time I handed that to a single long session, I watched the quality curve bend down. Task one came back sharp. By task five the model had quietly dropped half the constraints I set at the top.

The problem isn't the model

It's the architecture. A long context window is not a filing cabinet. It's a crowded room where the earliest instructions get drowned out by everything said since. The industry name for this is context decay. The usual response is a bigger prompt library: more rules, more examples, more reminders stacked at the top. That makes the room louder, not clearer.

So I stopped writing prompt libraries and started building infrastructure. The methodology doesn't live in a prompt the model might reread. It lives in code that forces the sequence whether the model is paying attention or not.

The pattern

I call it do-work. A complex request gets decomposed into independent requirement units before any work starts. REQ-001, REQ-002, and so on down the list. Each unit runs in its own fresh sub-context, and the model sees only three things: the workspace rules, that one requirement, and the reference material it actually needs. It does not inherit the conversation that came before.

When a unit finishes, its output is written to disk and committed to git as its own change. Then the working context is thrown away. The next unit starts clean.

The code ships with the page

github.com/HR-AR/claude-code-skills — the do-work skill and the rest of the harness, open source.

Why it holds

Task five gets the same quality floor as task one, because to the model, task five is task one. There is no accumulated drift to fight, because nothing accumulates. Each commit is a checkpoint. If one unit comes back weak, I see it in the diff and rerun that unit alone, instead of untangling a 90-minute session to find where it went wrong.

The counterintuitive part is that the win came from giving the model less, not more. Every instinct says a smarter assistant should hold the whole problem in its head. In practice, the whole problem in its head is exactly what degrades the work. Isolation beats memory.

Methodology as infrastructure

A framework written in a prompt is a suggestion. A framework written into the harness is a constraint the model cannot skip when it gets sloppy, because the harness never gets sloppy. The same idea runs through everything I build: the pipeline that scores its own output, the rules that fire on every file save, the scheduler that runs the follow-up whether or not I remember it.

Prompt libraries ask the model to behave. Infrastructure makes misbehaving impossible.

I would rather build the second thing.
